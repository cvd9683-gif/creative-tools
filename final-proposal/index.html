SAY: Show Up is the practice coach I built for the midterm. You pick a challenge, get a brief, and run a timed sprint — but the designing happens in Figma, Illustrator, or on paper. When time's up you paste your export onto a wall inspired by wheatpasted posters in NYC, and you can ask for an AI critique if you want one. In class testing, the big surprise: people treated it like a canvas. They tried to design inside the timer. The floating timer and the "New" mission button were unclear. The Wall was hard to move around, friend mode hung when the camera prompt was ignored, and the AI feedback sometimes failed on the first click. Some of that is fixed. Some isn't — that's what the final would be about. SAY: For the final, I wouldn't add a pile of features. I'd make the one loop — challenge, sprint, upload, reflect — impossible to misread, and make it more playful. Before: today's sprint has eight stages, three buttons and three outbound links. That's why it reads like a workspace. After: a small ticket-shaped timer with three stages, one button, and no text inputs at all — and the sprint ends by showing you the empty spot on the Wall where your piece will go. Pasting it up plays a brush sound, because the moment of showing up should feel like something. The same pass covers the three things testing flagged: a timer you understand (and that says honestly when it can't float), a Wall that opens on your newest piece, and feedback that's one tap with a clear failure state. Maybe, as an extension: community challenges. Someone posts a challenge, others join with a link, and everyone's work is revealed together on a shared wall. In round 4 of testing, someone wrote "SHARE" with a star. No marketplace, no payments. The question I'd test on Nov 24: after pressing Start, do people leave Show Up to design — without being told twice? DETAILS / UNCERTAINTIES • The "after" is a sketch, not built. Stage names (Plan / Make / Wrap) are placeholders to test. • Floating timer: keep Document Picture-in-Picture where it works; where it doesn't, say so plainly ("Keep this tab open — the timer will chime") instead of a widget that looks like it floats. • Sound: paste-up swish + end-of-sprint chime. There's already a chime setting in the code. • Wall: open on your newest piece, then let you roam. Fix the help text overlapping the controls. • Feedback: decide whether the default is Skip; show one clear message if the critic fails, with "try again". • Community challenges — what exists: the code already writes a shared challenge record with a member list when you start a "together" mission, and invite links work. What doesn't: nothing reads other people's pieces yet; the Wall only shows your own. Needs: a shared gallery query, Firestore rules so members can read each other's pieces, a reveal time, and fixing the account-scoping bug first. • How I'd measure the test question: watch 4–5 people; note whether they switch to Figma/paper within ~1 min of Start, and whether they type or click inside the timer.

Idea 2 · AI usage companion · the live widget

A carnival derby for your open AI chats

Example: making a gig poster with three chats open. One lane per chat, one glance to see which needs you.

Sketch · sample chats

What moves what

🐎 Horse

A step you mark done toward your checkpoint.

💧 Water

Messages you sent this session. Counted, not judged.

● Light

Running, ready, or waiting on you, where the page shows it.

The twist

At the carnival, more water = faster horse. Here it never does.

SAY: Idea two is a small companion for when you're juggling several AI chats. Here's an example: I'm making a gig poster. I have Claude writing headline options, ChatGPT suggesting palettes, and Gemini looking up venues. The look comes from the carnival game where you shoot water at a target and little horses race along parallel tracks. One lane per chat, labeled with the tool and what it's for. The light tells you if a chat is still writing, finished, or waiting on you. Open jumps to that chat; Handoff starts a summary you can carry to another tool. The important design decision is what the horse means. At the carnival, more water makes your horse go faster — that's exactly the loop I don't want. So here, water is just the messages you've sent: visible, counted, not judged. The horse only moves when you mark a step done toward a checkpoint you chose, like "pick the final headline". If the water keeps rising and the horse doesn't move, the widget gently asks if you want to check in — not that you're doing it wrong. Sound idea: a soft bell when a chat finishes, so you can stop watching tabs — and no sound for sending. WHY THE HORSE ISN'T TOKENS, MESSAGES, OR COMPLETION • Tokens consumed: not visible for consumer chat plans (see slide 5), and moving forward on tokens rewards using more. • Messages exchanged: easy to count, but it's the carnival's water — more prompts = faster horse is the addictive loop. • Response completion: a yes/no moment per message, already shown by the light. "Done generating" ≠ "useful". • Actual task progress: no tool can measure it from outside. So the person marks it — self-reported, labeled that way. → Chosen meaning for this sketch: steps the person marks done toward their own checkpoint. WHAT'S OBSERVABLE (details on slide 5) • Running / ready: a Chrome extension content script can watch the chat page for the stop button / streaming indicator — NEEDS TESTING, it depends on each site's markup and can break when they redesign. • "Needs you" = answer finished and you haven't looked at that tab since. Inferred, not reported by the service. • Message count: counted by watching your sends on the page — NEEDS TESTING. Only for sessions where the extension is running. • All chats/tasks in this sketch are sample data. THE DESIGN TENSION I want feedback on: making usage visible could make it more game-like and compulsive. No streaks, no points, no win state for sending. The finish line is the checkpoint you chose.

SAY: The widget is the glance. The report is something you open on purpose — mid-task or at the end. Everything on this slide is sample data. Left: where each number comes from, labeled. Messages are measured by the extension. Tokens are an estimate from text length — not the provider's count. Plan usage: Claude shows it as progress bars in its own Settings > Usage page, but there's no API for an extension to read it, so the report says so and links there. And then what you said: was each chat useful? Middle: patterns, framed as questions. "You asked for a new headline five times with 'make it punchier'." That might be healthy exploration or it might be stuck — only you know. The suggestion comes from the selected conversation, and "show me where" jumps to the messages it's based on. Right: an editable handoff — goal, what's decided, what you tried, what's still open, links, and the exact next step — so you can carry the work into another tool or a fresh chat without starting over. What it won't do: treat time in a tab as AI working time, call a longer session wasteful, or score your prompts. HOW EACH PART WOULD WORK — see slide 5 for sources • Measured message counts: only for chats where the extension was running, on supported sites. • Token estimate: a rough characters→tokens rule (or a tokenizer for one model). Always labeled "≈ estimate". Exact counts only exist where the person uses a developer API, which returns token usage in each response. • Provider allowance: Claude Pro/Max shows % progress bars and reset times in Settings > Usage (5-hour session limit + weekly limit), and in-app warnings like "Approaching session limit" (support.claude.com/en/articles/11647753, /9797557, /12466728). ChatGPT reportedly has a similar Settings → Usage page and Gemini notifies when limits refresh (both from search excerpts only — reopen help.openai.com/en/articles/20001625 and support.google.com/gemini/answer/16275805 before citing). No documented API exposes any of these to another app. Scraping that page would hit the same terms issue as below, and gives percentages, not tokens. So: "not readable here" + link. Never show a made-up "remaining tokens". • Exact token counts exist only on developer APIs: Anthropic responses include usage (input/output tokens) and anthropic-ratelimit-*-remaining headers (platform.claude.com/docs/en/api/rate-limits); count_tokens is itself "an estimate" (…/build-with-claude/token-counting). The Admin Usage & Cost API is "unavailable for individual accounts" (…/manage-claude/usage-cost-api). • Usefulness ratings: entered by the person, 1 tap per chat. • Pattern detection: simple and local — e.g. repeated near-identical requests in one chat. Neutral wording. • Prompt suggestion + handoff: the person selects a conversation (from the page, or pasted/exported), and only that text is sent to a model (e.g. Claude via the Messages API) with a prompt that must cite message numbers. Output is a draft the person edits. Needs explicit consent each time — this is chat content. • Time: I'd only show timestamps the page gives (when you sent, when the answer finished), never "minutes the AI worked".

Browser extension vs desktop app • Chrome MV3 content scripts can read and change pages the extension has host permission for (EXCERPT: developer.chrome.com/docs/extensions/develop/concepts/content-scripts). Badge text via chrome.action, notifications, chrome.storage (EXCERPT). • Tabs API gives title/URL only with tabs or host permission (EXCERPT: …/reference/api/tabs). • An extension can't see the ChatGPT/Claude desktop apps — no documented route. • Desktop app: macOS needs Accessibility and/or Screen Recording permission (EXCERPT: support.apple.com Mac Help); Windows UI Automation can read other apps' UI (EXCERPT: learn.microsoft.com uiauto-clientsoverview).
